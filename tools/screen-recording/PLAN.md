# Screen-recording skill: implementation plan

## Goal and boundary

For each example, inspect the app, propose a **3–5-feature story** and desktop-web or mobile-web presentation, get approval for the **actual scenario and its captions**, then run that scenario against a **local dev server by default**. Publish a matched GIF and MP4 for each approved take, retain the raw WebM as an ignored working master, and report what was verified. Deployment is an explicit, exceptional choice, never a standard step. Mobile-web means a phone-sized/touch-enabled browser, not a native iOS/Android app.

This directory contains local copies of the source we intend to adapt; the workflow must not fetch an upstream recorder at runtime. Daybreak is the first completed pilot: its approved scenario runs on disposable local state, its check passes, and the preferred full-screen GIF/MP4 pair is at `daybreak/demo/demo.gif` / `daybreak/demo/demo.mp4`. The original banner pair is kept at `daybreak/demo/demo-banner.gif` / `daybreak/demo/demo-banner.mp4`. The vendored Demotale engine includes a wrong-origin fix and a configurable interstitial presentation (`SOURCES.md`); it typechecks, passes 233 unit tests, and builds locally. The reusable Pi entry point is `.pi/skills/screen-recording/SKILL.md` (usage: `tools/screen-recording/README.md`). It has now been exercised end-to-end on **eventraum**: an approved five-scene English-captioned story, fresh local UI build and state for each run on port 8792, passing check/capture and reviewed assets at `event-raum/demo/demo.gif` / `event-raum/demo/demo.mp4`. Its ~68-second GIF is 720×450 at 5 fps (9.6 MiB, embedded in the app README); MP4 is 1280×800 (4.1 MiB). See `event-raum/demo/README.md`. **Learning Trail** is the third completed desktop example: fresh local state on port 8793, validated starter-workbook round trip, five checked feature scenes plus the approved applet.one closing card, and successful capture/export review. Its ~77-second pair is at `learning-trail/demo/demo.gif` (720×450, 5 fps, 9.7 MiB) / `learning-trail/demo/demo.mp4` (1280×800, 30 fps, 4.0 MiB); see `learning-trail/demo/README.md`. The other three examples, including mobile-web, have not been recorded.

## Code inspection and selection

- `vendor/demotale/` is the **primary engine**: its `src/demo.ts` implements watchable Playwright steps (`card`, `say`, `step`, `spotlight`, animated `click`, paced `type`, `note`, `redact`) and captures a timestamped timeline. `src/overlay.ts` draws the captions, title card, spotlight, and cursor **in the browser video**. `src/playwright.ts` handles `webServer`, recording, prepare-versus-demo runs, and an unrecorded `check` mode. `src/render.ts` / `src/ffmpeg.ts` convert the WebM into MP4/GIF; `src/captions.ts` writes VTT and a transcript. The `test/` suite and templates are also copied so we can change these pieces safely. This already covers most of the capture pipeline.
- `vendor/pagecast/` is a **later optional visual-effects donor**, not the primary recorder. `src/recorder.js` writes interaction bounding boxes and timestamps to a timeline; `src/zoom.js`, `src/converter.js`, and `src/remotion/` use those to add tooltip/zoom/pan effects. Its session-oriented MCP design overlaps with Demotale. Do **not** combine two browser sessions or two simultaneous recorders. If we want zoom, adapt the timeline/export logic behind Demotale's own step events, then test it on phone-sized captions before enabling it by default.
- `vendor/demo-gif-template/` holds a local copy of the agent skill instructions and an example Playwright capture script. Its useful idea is that the **script is committed and rerunnable**, with an explicit GIF size budget. It has no captioned-story engine and is not the runtime recorder.
- Demosmith MCP was inspected but **not copied**: `src/collector/collector.ts` logs per-action evidence and timestamps; `src/generator/subtitle.ts` produces subtitles; `src/generator/gif.ts` actually makes a slideshow from step screenshots (rather than converting the full-motion recording), and it bundles `ffmpeg-static`. Those features are already covered by Demotale for our use case. Its repository contains no LICENSE file (although its package.json declares MIT), so avoid copying from it until licensing is clarified.

## Local structure

- `.pi/skills/screen-recording/SKILL.md` — project-local Pi skill (now present): inspect example, draft storyboard, **stop for approval**, write/adjust scenario, run `check`, record, inspect output, report. Keep the approval gate in the skill, not in an automatic `postinstall` or CI job.
- `tools/screen-recording/vendor/demotale/` — the local, editable recording engine (already copied). Keep its LICENSE and NOTICE when changing or distributing it. We can prune unused CLI features after a working pilot, rather than reimplement its core.
- `tools/screen-recording/vendor/pagecast/` — optional zoom/export donor (already copied); keep its MIT LICENSE with any copied substantial code.
- `<example>/demo/storyboard.md` — the **human-readable proposal**: audience, 3–5 features, desktop/mobile choice, ordered scenes, exact caption copy, setup/data disclosure, final frame, and estimated length.
- `<example>/demo/*.demo.ts` — the **approved executable Playwright scenario**. Assert the visible result for every scene. Add a `<example>/demo/*.prepare.ts` only for off-camera fixtures. Commit both so a future recording can be regenerated.
- `<example>/demotale.config.ts` and `<example>/playwright.config.ts` — local `webServer` command (Daybreak starts `applet dev` in a disposable source copy), readiness URL, viewport, output path, caption display, and redactions. Use different configs/ports if examples run concurrently.
- `<example>/demo/output/` — ignored working files: raw WebM, reports, frames, auth state, drafts. Copy **both** final assets to `<example>/demo/<name>.gif` and `<example>/demo/<name>.mp4`. Keep recording details in `demo/README.md`; the main app README only embeds the preferred GIF. Keep the same basename for each take and don't commit private state or raw browser recordings.

## Approval contract

1. Inspect the README, app, scripts, and UI locally; propose a concise storyboard **without running a destructive setup or publishing**. In the proposal, identify which feature is real, seeded, simulated, or unavailable.
2. After the user edits and approves that proposal, save it together with the scenario file and a source commit ID. **The agent must ask again** if scene order, captions, target URL, setup, or data-changing behavior needs a material change. No autonomous substitution of a different demo flow after approval.
3. Only then run a dry check and present its frames/report; fix broken selectors without changing the story. On capture failure, preserve the failed take for debugging and report the discrepancy; do not publish it as the demo.
4. Review the final GIF visually and report its duration, dimensions, bytes, assertions passed, caption text, and any disclosed seeded behavior. Get separate approval before changing an app's code or using a deployed URL.

## Recording pipeline

1. Preflight: Node, pnpm, Applet CLI, browser, and system `ffmpeg`; determine each example's build step (`sidechat` and `event-raum` build assets before `applet dev`). Do not install `ffmpeg-static` by default: its binary has separate GPL-related redistribution considerations. Do not assume `networkidle` for apps with polling/WebSockets.
2. Start the local server via the recorder's Playwright `webServer` option; wait for an actual reachable URL. Daybreak's pilot starts `applet dev` in a fresh copy under ignored `demo/output/`, using port 8791 and fictional accounts. For another pilot, `clanker-station`'s synthetic `/demo` route is read-only; a mobile-web story for `rep-by-rep` requires isolated passphrase/data state.
3. Prepare fixtures **off camera**. Before recording any stateful app, verify the Applet dev server's local persistence path and use a disposable copy or resettable state; a fresh browser context alone does not reset a Durable Object. Never use a production tenant or hard-code real credentials. `daybreak` requires two fresh demo accounts; `event-raum` needs a safe booking/admin fixture; `learning-trail` needs a fixed learner/workbook state; `sidechat` may use its demo login only if it is isolated from saved personal data.
4. Use semantic Playwright locators and short assertions. Start video with a title card, explain each feature **before** its action, hold the verified result briefly, and finish on an understandable final frame. Daybreak uses `captions.display: 'dark-screen'`: a large explanation fades in/out over a dimmed screen, then the action plays unobstructed. The engine also supports `light-screen` or the original `banner` display. Text is burned into the recording; VTT/transcript are separate outputs. Editing captions *after* filming without replay would require a distinct post-production feature.
5. Run the vendored `check` pass first and inspect its screenshots; run the recorded pass only when checks pass. Close the browser context to finalize WebM. Convert using the local ffmpeg code's palette-generation GIF pipeline; choose dimensions/fps against a practical README size budget (Daybreak's 53-second full-screen GIF is 800×500 at 7 fps, ~7.8 MiB). Keep the MP4 alongside the GIF in `demo/`, and retain the raw WebM in ignored output rather than sacrificing legibility to force a single giant GIF. Split a long 3–5-feature story into short GIFs if needed.
6. Include a note such as “Synthetic demo data” when applicable; redact secrets before the first frame, and examine frames for credential and PII leaks. Clean up dev processes and disposable state, never delete the user's real local or hosted app data.

## First implementation increments

1. **Pilot (done):** `daybreak` has an approved five-scene storyboard, checked-in prepare/record scripts, a fresh Applet source snapshot for every run, passing dry check, and captioned GIF. See `daybreak/demo/README.md`. Its local `file:` dependency requires building Demotale before `pnpm install`; the package can be renamed/localized later.
2. **Pi skill (validated on three examples):** `.pi/skills/screen-recording/SKILL.md` guides proposal, approval, checks, recording and paired asset publication. It drove eventraum's and Learning Trail's approved English-captioned desktop demos through check, capture, visual review and paired publication. This is orchestration/instructions, not a new binary; deterministic browser, overlay and encoder logic stay in the checked-in engine.
3. **Generalize:** validate another example (including mobile-web `rep-by-rep`) and implement per-example prepare/reset strategies before attempting all six. Add optional Pagecast-derived zoom only if ordinary spotlight/cursor effects prove insufficient.

## Acceptance criteria

- An approved, checked-in scenario and local `pnpm dev` reproduce the same narrated story without deployment or manual mouse input.
- `check` fails quickly on missing UI and does not publish a recording; final captures contain captions, visible taps/clicks, and assertions for each promised feature.
- A rerun starts with clean or explicitly disclosed demo state; no real credentials/PII are in the frames or committed artifacts.
- Final GIF is watchable on a phone/README; the matching MP4 and source script are committed in `demo/`, raw WebM is retained locally, and the pair can be regenerated after UI changes.
